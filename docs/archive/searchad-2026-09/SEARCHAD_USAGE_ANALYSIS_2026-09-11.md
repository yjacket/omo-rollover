- 완료 작업 수

- OMO가 기록한 비용 환산값

캐시 적중률은 다음 식으로 계산했다.

`cacheRead / (input + cacheRead + cacheWrite) × 100`

### 판정

`invalid_state`가 실제 로그인 장애를 뜻했다면 재인증 후 실제 Claude 호출도
실패해야 한다. 그러나 같은 점검 결과가 계속되는 동안 실제 Claude 자식은
폴백 없이 성공했다.

또한 공급자만 지정한 점검은 `provider_not_found`라고 하면서 `default`
로그인 계정도 동시에 표시했다. 모델 목록에는 같은 공급자가 정상 등록돼 있다.

따라서 현재 증거로 확인한 사실은 다음과 같다.

1. Claude 로그인이 실제로 끊긴 시점은 확인되지 않았다.
2. 마지막 검증된 정상 Opus 사용은 12:37:34 KST다.
3. CLI의 첫 `invalid_state` 관측은 16:52:25 KST다.
4. 이 두 시각 사이에 실제 장애가 있었다는 증거는 없다.
5. 현재 실제 Claude 구독 레인은 작동한다. 재인증 후 Haiku 실호출로 확인했다.

추정 원인은 `omo auth check`가 확장 공급자인 `claude-sdk-oauth`를 완전히
로드하지 못하거나, 해당 공급자의 인증 상태 형식을 해석하지 못하는 것이다.
이 내부 원인은 로그만으로 확정하지 않았다.

`credential-pool-state.json`에는 2026-09-09의 `rate_limit` 기록만 남아 있고
파일도 그날 이후 갱신되지 않았다. 이는 2026-09-11의 인증 상태를 판정하는
근거로 사용할 수 없다.

## OMO beta.53 영향

현재 설치 버전은 다음과 같다.

- OMO: `5.0.0-0.beta.53`
- senpi: `2026.9.10-2`

따라서 별도 업그레이드는 필요하지 않다.

이 릴리스의 Claude 구독 우선 라우팅은 향후 기본 에이전트가 유료 API보다
구독 레인을 먼저 선택하도록 돕는다. 현재 사용자 카테고리도 이미
`claude-sdk-oauth`를 첫 순서로 지정한다.

그러나 실패 후 연속 실행 차단은 `ulw-loop`와 `ulw-execute`에만 적용된다.
이번 SearchAd 세션에서 반복된 것은 일반 `goal-continuation`이므로 직접적인
수정 대상이 아니다.

새 `model_profile` 기능도 현재 비활성이다. `~/.omo/omo.jsonc`에
`model_profile` 또는 `model_profiles`가 없고, 전역 기본 모델은 현재
`openai-codex/gpt-5.6-sol`이다. 재개 세션은 모델 프로필 적용 대상도 아니다.

## 권고

1. `omo auth check`만으로 Claude 구독 상태를 판정하지 않는다.
2. 인증 확인이 필요하면 도구를 쓰지 않는 짧은 `quick` 자식으로 실호출한다.
3. 장기 오케스트레이터는 단계 경계에서 압축하거나 새 세션과 인계 문서로
   넘긴다.
4. `goal-continuation` 호출 수와 실패 후 재개 조건을 별도로 제한한다.
5. 모델 변경 전후에 Codex `/status` 또는 사용량 화면을 기록해 실제 포함 한도
   감소량을 비교한다.
6. 자식 모델 폴백보다 메인 모델 선택과 메인 문맥 크기를 먼저 관리한다.
7. 새 모델 프로필을 쓴다면 기본 `deep work`나 `simple work`를 그대로 쓰지
   않는다. 두 프로필 모두 Codex 모델을 첫 순서로 사용한다.
8. 현재 Codex Pro x5 변경 이후에도 긴 자동 실행은 짧은 시간에 새 한도를
   소모할 수 있으므로, 세션 압축과 연속 실행 제한을 함께 적용한다.
